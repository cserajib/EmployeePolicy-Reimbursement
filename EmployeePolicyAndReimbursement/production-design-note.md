# Production design note

**Initial changes.** 10,000 requests/day averages only about 0.12 requests/second; peak concurrency and approval wait time, not daily volume, should drive capacity planning. I would first replace the local JSON file with a versioned, auditable policy store and validate ingestion: the supplied data contains two simultaneously effective Atlas home-office limits. Enforce tenant, role, and identity from authenticated server-side claims, not request fields. Keep draft/unapproved policies out of answers, preserve effective-date history, and return “needs human review” when approved sources conflict. Treat policy text as untrusted data; injection-pattern filtering alone is not a security boundary.

**Deployment.** Containerize the API and deploy to Azure Container Apps, initially with modest autoscaling and private ingress. Use a managed relational database for policy and approval state, Azure Service Bus for durable approval work, Key Vault for secrets, and managed identities for service-to-service access. Keep answering synchronous only when it is fast; submit slow approvals as durable, idempotent jobs with explicit states, retries, deadlines, and a human escalation path. Load-test realistic bursts before setting scale limits or promising latency.

**Key risks and controls.** Personal information could leak through logs, citations, batch errors, or cross-tenant access: minimize collected data, redact logs, encrypt in transit/at rest, restrict access by least privilege, set retention/deletion rules, and audit reads and approval changes. Approval rules are only partially documented, so wrong routing, duplicate actions, stale policy, and silent retries could cause unauthorized decisions; require a documented state machine, immutable decision history, idempotency, and manual review for uncertain cases. Operationally, the current file-backed data, unbounded batch work, and basic health response do not provide durable state, backpressure, or dependency readiness. Add request/batch limits, rate controls, readiness checks, dashboards and alerts for latency, queue age, errors, and ambiguous answers, plus tested backup/restore and incident procedures.

**Before committing a delivery date, clarify** peak/burst traffic and latency targets; identity provider, tenant boundaries, data residency and retention obligations; approval roles, transitions, SLAs, escalations, and override authority; authoritative policy owners and conflict-resolution rules; and required integrations, availability target, recovery objectives, and acceptance/security testing.
